Scripture Alone · A proposal to publishers

How a licensed translation stays safe in an open-source Bible

Our source code is public. The reasonable question a publisher asks next is how their text could possibly be safe in it. This is the answer — a format, an implementation and a set of tests, including an honest account of what it cannot do.

Blaine Miller · Updated September 2026
The claim

Stated precisely, so it can be checked

A licensed translation ships as a signed, encrypted package. The app can read it. A person holding the file cannot read it without the key. And the publisher decides — in data the app enforces, not in a PDF in a drawer — what may be done with the text once it is open.

The plaintext never exists as a file

Chapters are decrypted one at a time, in memory, on demand. A whole Bible in the clear never lands on disk, and the decryption interface is shaped so that it cannot.

The terms travel with the text

The permission policy sits in a header signed by the publisher's own key. Edit the policy and the signature fails; the package stops opening.

The publisher holds the keys

The packaging tool runs on the publisher's machine with the publisher's keys. We never receive the plaintext and never hold the key that decrypts it.

Search doesn't undo any of it

The index is sealed exactly like the text. A search opens one or two of 256 encrypted buckets and decrypts only the chapters its hits are in. There is no plaintext index.

The objection

Why open source is the stronger position, not the weaker one

The instinct that public source makes text less safe is understandable, and it is the opposite of how cryptography is assessed. Kerckhoffs's principle, the foundation of the field since 1883, holds that a system must stay secure when everything about it except the key is public. Every cipher a publisher already relies on — the TLS in front of their storefront, the disk encryption on their staff's laptops, Apple's Secure Enclave — is public in exactly this sense.

A scheme that needs its design kept quiet is one that has not been examined.

The practical consequence

A closed-source Bible app is in the identical position. Any app that reads a licensed translation offline must put a key on the reader's device. That is true of every major Bible app on the App Store. The difference is not whether a key is on the device — it is whether anyone outside can confirm what the app does with it.

A fork gets the code, not the text. The repository contains no content key and no signing key, and the packaging tool refuses to run against a key inside the working tree. Anyone may clone Scripture Alone; nobody who does can decrypt a licensed package, because the secret was never in the thing they cloned.

The security of this design rests on the key and the signature. That is the correct place for it to rest.

The header is plaintext on purpose. Anyone may see what a package claims to be, who signed it and under what terms, without holding any key. Secrecy of the terms was never the goal; integrity of them is. Here is the header of the package this app actually ships, printed with no key at all:

  "chapters": [ { "book": 1, "chapter": 1, "verses": 31, "offset": 0, … }, … ]

Every permission there is true because that package is the American Standard Version, which is public domain — sealing it must not cost its readers anything. A licensed package is where those fields earn their keep.

What each chapter is sealed against

Each chapter is sealed separately with AES-256-GCM, and its authenticated associated data binds the package id, the translation id, the chapter, and a SHA-256 of the header. Four attacks therefore fail loudly instead of silently:

AttackResult
Edit the policySignature fails; the package does not open.
Re-sign with another keyThe key isn't pinned; refused before its terms are read.
Move a chapter between packagesThe package id in the sealed data no longer matches; the seal fails.
Replay a chapter across a terms changeThe header hash in the sealed data no longer matches; the seal fails.
Enforcement

The terms reach the buttons, not just the file

A permission that only the file format understands is a promise. These are read from the signed header and enforced at the control a reader actually touches:

Policy fieldWhat the app does when it is false
allowCopyCopy is disabled in the selection bar.
allowShareShare text and share links are withheld.
allowVerseImagesNo verse image can be rendered.
allowNotesExportExporting notes with their verses is refused, and says why.
allowExternalHandoffThe text is never handed to another app to render or speak.
allowOfflineStorageThe package is not copied into the library at all.
maxQuotationVersesCopy and share disable past the cap, naming the limit.
expiresPast the date the package refuses to open.
Search

Sealed, and measured rather than asserted

A packaged translation is fully searchable — phrases included — with no plaintext index at any point. Postings carry word positions, so a phrase is an adjacency check rather than a scan, and they are bucketed by a keyed hash and sealed like chapters. A hashed-token index left in the clear would, for a Bible, let someone align frequencies against a public edition until every hash was identified. That is precisely what we did not build.

1bucket of 256 opened by the commonest word in scripture
≤30chapters of 1,189 decrypted for that search
0chapters decrypted by a search with no matches
16size classes the 256 buckets fall into, after padding

What remains visible to someone without the key is the size of 256 buckets. Recovering word frequencies from that is a 256-way subset-sum over tens of thousands of unknowns, and its answer would be "bucket 37 probably holds the", which decrypts nothing. Padding every bucket to the largest would cost 6.5× the index size; we measured that rather than guessing, and the padding quantum is a signed header parameter a publisher can change.

Honesty

What this does not do

The key is on the device, and a determined attacker can recover it

The content key is derived with HKDF from a seed injected at build time, then sealed to a Secure Enclave key generated on that device and marked this-device-only. The keychain holds ciphertext. That closes every route that actually happens — a copied keychain, a device backup, a file-system dump — and it does not hide the seed from someone disassembling the binary. Nothing on a general-purpose computer does.

This raises the floor, not the ceiling, and it is the same floor a closed-source app stands on. We would rather describe it accurately than imply a ceiling that doesn't exist.

A search leaks its own pattern to someone watching the device

Which buckets a query opens is visible to something observing file access on a device it controls. That is inherent to any encrypted index not read in full, and reading it in full would mean decrypting the whole index per keystroke. It reveals that two searches were for the same word, not what the word was.

The analogue hole is always open

Any reader can screenshot a page, and a patient one can script scrolling and run OCR. That is true of every Bible app, every e-reader, and every printed book with a photocopier next to it.

This design gives you the same protection a closed-source app gives you, plus the ability to verify it, plus enforcement of your specific terms in code rather than in correspondence. — and not protection against a determined adversary, because nothing is
The proof

It isn't a demonstration. It's the translation you open by default.

The obvious way to prove a format is to ship a sample beside the real translations. We did that first, and it proves only that a code path compiles.

So the American Standard Version now ships as the package — no plaintext database in the app to fall back on, and it is the translation Scripture Alone opens by default. Every reader, on every launch, derives the content key, unwraps it from the Secure Enclave, verifies an Ed25519 signature and reads chapters decrypted one at a time. Searching it searches the sealed index. If any of that broke, the app would not open on a fresh install.

That is a stronger claim than a demonstration can make, and it is the reason to prefer it. A sample nobody selects proves the code compiles. A default translation proves the format survives contact with real use — real size, every chapter, every search, on every device, for as long as the app is in the store.

Two claims, deliberately kept on separate artefacts

The shipped package permits everything, because its text is public domain and its readers must lose nothing. That a package can forbid things — and that the app obeys, at the control the reader touches — is proved separately, against packages built to forbid them. Proving both with one artefact would let a weakness in either hide behind the other.

For your engineers

What to read, and what is still open

Four files carry the whole claim: TranslationPackage.swift — where the part worth reading is the sequence of checks performed when a package is opened, and the two private functions that open a sealed box — together with PackagePolicy.swift, PackageSearchIndex.swift and TranslationRights.swift, plus the packaging tool. The format is implemented twice, in two languages, so a divergence shows up as a failing test rather than as a package that won't open on your desk.

Still open, so nobody discovers it later: the attested key-delivery route (a small endpoint that releases a key only to a genuine build, which we will build if your terms need it) is specified but not written; there is no watermarking, which we can add and would describe to you as a deterrent rather than a protection; and no package has yet had to hold two publishers' keys at once, though the design is namespaced for it.
